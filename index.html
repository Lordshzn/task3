Project Description

TALA is a desktop registrar document-request and counter-queue application intended for students, Registrar Staff, Office Staff, and administrators. Students use a self-service kiosk to look up student information, request registrar documents, receive a queue ticket, and check request progress using a reference number. Staff manage the counter queue and process document requests through office-specific workflows. Administrators configure the system, staff accounts, offices, reports, workflows, and data backups. A separate serving display presents counter activity to people in the service area.

The system uses PostgreSQL to store requests, queue tickets, lifecycle information, workflow configurations, accounts, notifications, and audit records. TALA can send status messages through an external SMS provider. The student lookup API and SMS delivery provider are external dependencies; their availability and data are not guaranteed by the application alone.

System Review

1. System Purpose

  • Give students a consistent way to request documents and track progress.
  • Organize in-person service using numbered queue tickets and counters.
  • Allow authorized staff to manage requests and their office processing.
  • Provide status visibility without exposing internal staff notes.
  • Keep records of queue actions, lifecycle changes, and notifications.

2. Target Users and Roles

Students
Look up their student information, select requested documents and request details, receive a queue/reference number, and check request status using the reference number.
Registrar Staff
Handle counter queue tickets and Registrar's Office workflow steps. The service layer restricts Registrar Staff step updates to steps assigned to the Registrar's Office.
Office Staff
Work on workflow steps assigned to their office. The service layer restricts an Office Staff account linked to an office to that office's steps.
Admin
Has administrative privileges for staff account creation, workflow and office configuration, lifecycle administration, reporting, backups, and other admin tools.
Public Display Viewers
See which tickets are being served, which are waiting, and recently completed tickets. This display is not an account role.

The database recognizes Admin, Registrar Staff, and Office Staff roles. The visible dashboard has separate Admin-only controls; service-level office permissions also apply when staff update workflow steps.

4. General Request Journey

  1. Student enters a Student ID in the kiosk.
  2. Kiosk calls the configured student API and presents the returned student information for confirmation.
  3. Student selects one or more documents, a purpose, and a format.
  4. The application validates the document selection and submits the request to PostgreSQL.
  5. The database service creates a request, permanent reference number, request-document rows, and a queue ticket.
  6. The kiosk displays a confirmation with the queue number and reference number.
  7. Staff call and process the queue ticket at a counter.
  8. Completion of the initial queue transaction starts the separate document-processing lifecycle and creates its workflow snapshot.
  9. Authorized office staff update workflow steps and request status.
  10. Student uses the reference number to check public progress. SMS notifications may also be queued for configured status events.
  11. After all required office steps are complete or waived, staff can mark the request ready to claim, then claimed once the documents are released.
Important distinction: completing the counter ticket is not the same as completing or claiming the requested documents. Queue processing and document lifecycle processing are separate workflows.

Features

1. Student Kiosk

Student ID Lookup
Type an ID or use the on-screen keypad. The ID is sent to the API configured in services/studentApi.py. A 404 is treated as not found; other unsuccessful HTTP responses, connection failures, and invalid responses are presented as errors. The URL points to localhost; the API server and mock dataset are not in this repository.
Student Confirmation
The kiosk displays the returned student information so the student can confirm identity.
Document Selection
One or more of: Transcript of Records, Certificate of Enrollment, Certificate of Grades, Certificate of Good Moral, Honorable Dismissal, Authentication / Certification, Other Registrar Request. Each selection is stored as its own request_documents record.
Request Details
Purpose: Employment, Scholarship, Transfer, Internship / OJT, Personal Use, Government Requirement, School Requirement, Other. Format: Printed Copy, Digital Copy, Printed + Digital Copy. Purpose and additional information are stored on the request; document type and format are stored per document.
Submission Validation
The kiosk checks for a Student ID and at least one document. The database service independently rejects empty selections and removes duplicates. Purpose and format are not enforced as required by the database service.
Request Confirmation
Shows the queue number, reference number, and document selection.

2. Queue Management

Queue Overview
The dashboard lists queue number, student ID/name, document, counter, status, and queued time, with summary cards (pending, at counters, completed today, total today). Staff can search, filter, refresh, or use five-second auto-refresh.
Calling and Serving
Staff call the next waiting ticket or serve a selected one. The next-ticket query orders by queue position and uses row locking with SKIP LOCKED so two actions cannot claim the same row.
Ticket Actions
Complete, cancel / no-show, transfer to a counter, skip, and recall a skipped ticket. Completed queue transactions cannot be changed through the normal update.
Timing and Reporting
Timing data supports wait and service reports. Admins can run date-range reports and export CSV.
Live Updates and Serving Display
PostgreSQL queue changes publish notifications to the real-time listener. The serving display shows tickets by counter, upcoming tickets, and recently completed ones, with auto-refresh, clock, fullscreen, and optional call chime.

3. Document Request Lifecycle

Lifecycle Activation
When the queue transaction is completed, the application starts lifecycle tracking, snapshots the current workflow for the document, and queues an acceptance notification. A queue cancellation is separate from office-processing status.
Overall statusMeaning
REQUESTEDAccepted for processing after lifecycle activation.
UNDER_PROCESSINGProcessing is underway at one or more offices.
NEEDS_ACTIONStaff need an action or information; a reason is required.
READY_TO_CLAIMAll required office steps are completed or waived.
CLAIMEDDocument released. Normally set only from READY_TO_CLAIM.
REJECTEDRequest rejected; a reason is required.
CANCELLEDRequest cancelled; a reason is required.
Validated Transitions
The document service controls legal transitions. Changes are unavailable until lifecycle tracking has started and the initial queue transaction is completed. Required steps are checked before READY_TO_CLAIM. Terminal states are not freely editable; reopening is an audited admin operation.
Office Workflow Configuration
Admins configure versioned workflows per document type. Each has ordered steps with an office, step name, and required/optional flag. Saving creates a new version. Existing requests keep the snapshot taken when their lifecycle started.
Request-Specific Tracking
With no configured workflow, the system does not invent steps; authorized staff may add request-specific steps.
Step Management
Staff can start, complete, hold, resume, waive, unwaive, reset, or remove steps, depending on permissions and status. Steps may be started out of order; what matters is that all required steps are completed or waived.
Office Location
Tracked independently from step status. Staff may set or clear a location and add a note; progress can update it to the active or next pending office. It is cleared when the request is claimed.
Public and Internal Information
Steps keep public remarks separate from internal notes. Public tracking does not expose internal notes or staff identities.

4. Public Progress Tracking

Reference Lookup
Reference numbers are normalized to uppercase. Unknown or invalid references get a generic not-found message.
Information Shown
Depending on state: reference, queue number/status, documents, overall status, timestamps, estimated completion, current office and step, public remarks, status reason for selected states, and claiming instructions when ready.
Rate Limiting
Lookups are throttled by a configurable limit and window. The limiter is in-process, so counters are local to that running process.

5. Staff Accounts and Audit

Authentication
Credentials are checked against bcrypt password hashes. Inactive accounts are rejected. Successful logins can be audited.
Roles and Permissions
Admin, Registrar Staff, and Office Staff. Registrar Staff are limited to Registrar steps; Office Staff to their linked office's steps.
Account Creation
Admin can create Registrar Staff accounts. Username length is validated, passwords need at least eight characters and are hashed before storage.
Audit Log
Records administrative and operational events; Admins can inspect recent activity.

6. SMS Notifications

Events
Acceptance, under processing, step completion, needs action, ready to claim, cancellation, rejection, claimed/released, and office transfer, depending on the lifecycle operation.
Outbox and Delivery
Notification rows live in PostgreSQL. A background worker polls due rows and talks to SMS8. Delivery is asynchronous, so SMS failure never rolls back a lifecycle update.
Retries and Duplicates
Bounded exponential backoff up to the configured maximum. A database constraint prevents duplicates per request and event type. Staff can review status and errors and retry failures.
Preferences and Disabled Service
Event types can be enabled or disabled. If SMS is disabled or configuration is missing, messages are recorded as skipped.

8. Identifier and Queue Number Rules

Permanent Reference Number
Generated on the backend from a PostgreSQL sequence: configurable prefix, two-digit year, department code, and a sequence value padded to at least five digits. Concurrency-safe; values are not reused.
Queue Number
Q- plus an increment based on the largest number created on the database's current date. LPAD width is three, so numbers above 999 are not safely supported, and the max-plus-one query is not protected against simultaneous submissions.

Technical Overview

Programming and Code Walkthrough

Shortened excerpts of implementation patterns; not complete standalone files.

1. Program Startup

from system.config import Config
from controllers.kioskController import KioskController
import tkinter as tk

def main():
    Config.validate()
    root = tk.Tk()
    app = KioskController(root)
    app.start()
    root.mainloop()

if __name__ == "__main__":
    main()

Config.validate() checks required settings, tk.Tk() creates the window, the controller manages screens, and mainloop() handles events. The __name__ guard stops main() from running on import. admin.py creates AdminController, main.py KioskController, serving.py ServingController.

2. MVC Structure

Models (Student, Request, Queue) carry data; views under views/ draw screens; controllers switch screens and wire callbacks; services hold queries, validation, authentication, workflow rules, API calls, tracking, SMS, and real-time updates. This keeps SQL and business rules out of widgets.

3. Student API

response = requests.get(f"{cls.BASE_URL}{student_id}", timeout=timeout)
if response.status_code == 404:
    raise LookupError("Student ID was not found.")
response.raise_for_status()
return response.json()

Callers handle LookupError (not found), requests.RequestException (HTTP/network), and ValueError/TypeError (bad payload). BASE_URL is fixed to localhost and no server is included.

5. Validation and SQL Writes

document_types = list(dict.fromkeys(
    t.strip() for t in document_types
    if isinstance(t, str) and t.strip()))
if not document_types:
    raise ValueError("Select at least one document to request.")

connection = self.connection_pool.getconn()
try:
    with connection:
        with connection.cursor() as cursor:
            cursor.execute("INSERT INTO ... VALUES (%s, %s)", (a, b))
finally:
    self.connection_pool.putconn(connection)

with connection commits on success and rolls back on exception; finally returns the connection to the pool; %s parameters keep data separate from SQL. One transaction: upsert student, generate reference, insert request, insert document rows, insert WAITING queue row, return identifiers.

6. SQL Concepts

Primary keys, foreign keys (ON DELETE CASCADE), UNIQUE constraints, ON CONFLICT insert-or-update, RETURNING, indexes, and transactions.

7. Reference Number Generation

cursor.execute("SELECT nextval('request_reference_seq')")
sequence_value = cursor.fetchone()[0]
return f"{prefix}{year}{dept}{str(sequence_value).zfill(5)}"

The sequence is concurrency-safe. The queue number uses COALESCE(MAX(CAST(SUBSTRING(queue_number FROM 3) AS INTEGER)), 0) + 1, which is not atomic: two concurrent transactions can read the same maximum.

8. Authentication

password_hash = bcrypt.hashpw(
    password.encode("utf-8"), bcrypt.gensalt()).decode("utf-8")

Login uses bcrypt.checkpw(), checks the account is active, and audits success. A hash is not reversible encryption.

9. Lifecycle State Logic

SELECT COUNT(*),
       COUNT(*) FILTER (WHERE is_required = TRUE
                          AND is_waived = FALSE
                          AND status <> 'COMPLETED')
FROM request_tracking_steps WHERE request_id = %s

Ready only when at least one step exists and zero required, non-waived steps are incomplete. queue.status (WAITING, SERVING, COMPLETED) and requests.overall_status are different data.

10. SQL Safety and Permissions

Always use placeholders, never string concatenation. DocumentService checks office permissions before updating a step: Admin all offices, Registrar Staff Registrar steps, Office Staff their linked office.

11. Threads and Tkinter

def run_lookup():
    result = service.lookup(reference)
    self.after(0, lambda: self._render(result))
threading.Thread(target=run_lookup, daemon=True).start()

Slow work runs in a background thread; after(0, ...) queues the UI update on the event loop.

12. LISTEN / NOTIFY

A trigger publishes on the queue_updates channel after queue inserts, updates, and deletes. RealtimeService runs LISTEN queue_updates, parses the JSON payload, and calls subscribers, which then fetch current queue data.

13. SMS Outbox

Lifecycle code inserts the notification inside its transaction. SmsService's worker later sends to SMS8 and records sent, failed, or skipped. A remote outage cannot undo a valid update.

Business Rules to Remember

  • A request may contain multiple document selections, stored as separate rows.
  • At least one valid document type is mandatory at the database service.
  • The queue ticket is for in-person service; the reference number is for persistent identification and progress lookup.
  • Completing the queue transaction starts lifecycle processing; it does not mean the document is ready or claimed.
  • All required office steps must be completed or waived before READY_TO_CLAIM.
  • Only READY_TO_CLAIM requests can become CLAIMED normally.
  • Public tracking shows safe details, not staff-only notes.
  • SMS delivery is asynchronous and may fail independently.
  • A missing workflow is not replaced; staff may add request-specific steps.

Non-Functional Characteristics

Integrity: foreign keys and transactions. Access control: hashed passwords, role and office checks. Reliability: repeatable setup, outbox, bounded retries. Usability: guided kiosk, staff search and reports, public display. Responsiveness: LISTEN/NOTIFY and background threads. Limitations: depends on PostgreSQL, the localhost student API, and SMS provider availability.

Known Limitations and Points for Improvement

  • The student API and its mock dataset are not part of this repository.
  • The form always sends an empty additional_info.
  • The database service does not require purpose or format.
  • Queue numbers can exceed three-digit padding and race under simultaneous submissions.
  • The rate-limit state is in memory and not shared across processes.
  • SMS depends on an external provider and may be skipped, delayed, or fail.
  • Availability and records depend on the database, configuration, permissions, and external services.

Review Questions and Suggested Answers

Q1. What is TALA?

A desktop registrar document-request and counter-queue system. Students submit and track requests; staff manage queue service and office processing; administrators manage configuration and oversight.

Q2. Who are the system's users?

Students, Registrar Staff, Office Staff, and Admin. The serving display is a public view, not a role.

Q3. Queue number vs. reference number?

The queue number (Q- prefix) identifies a ticket in the day's in-person queue. The reference number identifies a request for later tracking and comes from a PostgreSQL sequence.

Q4. What happens when a student enters a Student ID?

The kiosk calls the student API. Not-found is handled as a lookup error; other HTTP, connection, or response problems are shown to the student.

Q5. How are multiple documents stored?

The request is in requests; each document and format is a row in request_documents.

Q6. What validation happens before creation?

The UI requires a Student ID and one document. The database service filters empty and duplicate types and rejects an empty result.

Q7. What does completing a queue ticket mean?

It completes the counter transaction and starts lifecycle tracking, not office processing or readiness for pickup.

Q8. When can a request become ready to claim?

After lifecycle processing has started and every required step is complete or waived.

Q9. Can staff claim directly from processing?

No. The normal transition requires READY_TO_CLAIM first.

Q10. How are workflows applied?

Admins configure versioned workflows by document type. At lifecycle start the current workflow is copied as a snapshot, and later changes do not alter it.

Q11. What if no workflow is configured?

No steps are invented; staff add request-specific steps.

Q12. What can students see when tracking?

Public-safe request, queue, status, office, step, timing, and public-remark details. Internal notes and staff identities are excluded.

Q13. How does SMS failure affect a request?

It is recorded and may be retried, but never rolls back the request or lifecycle transaction.

Q14. What protects staff accounts?

bcrypt hashes, rejection of inactive accounts, and role and office checks.

Q15. What is the queue numbering limitation?

It uses a daily max-plus-one with three-character padding, so numbers above 999 are unsafe and concurrent submissions can race.

Q16. Which external services does TALA need?

The student lookup API and SMS8, plus PostgreSQL for persistence.

Q17. What are the three entry points?

main.py (kiosk), admin.py (staff dashboard), serving.py (Now Serving display).

Q18. What does if __name__ == "__main__": do?

It runs the entry function only when the file is executed directly, not imported.

Q19. Why use %s placeholders?

They bind values separately from SQL text, preventing injection and handling escaping.

Q20. Why a transaction for request creation?

The student, request, document, reference, and queue writes are one logical operation; failure rolls back partial changes.

Q21. What does finally guarantee?

The borrowed connection is returned to the pool whether the operation succeeds or fails.

Q22. Why bcrypt?

It stores a salted hash; login verifies against it without storing the original password.

Q23. Why use after()?

It schedules UI work on Tkinter's event loop instead of touching widgets from a worker thread.

Q24. Purpose of LISTEN/NOTIFY?

The database signals queue changes; the listener prompts the UI to refresh.

Q25. What is the outbox pattern for?

Committing a notification with the business change, then sending it asynchronously so provider failure does not undo the change.

Q26. Which reference component is concurrency-safe?

The permanent reference (sequence). The daily Q- number is max-plus-one and is not.

Glossary

Queue Ticket
Number organizing a student's place in the in-person queue.
Reference Number
Persistent request identifier for progress lookup.
Request Document
One selected document type with its own format.
Lifecycle
Office processing after the initial queue transaction.
Workflow
Configured office steps that guide and record processing.
Workflow Snapshot
Workflow copy saved to a request when lifecycle tracking starts.
Required Step
A step to be completed or waived before READY_TO_CLAIM.
Outbox
Database-backed list of notifications awaiting delivery or recording results.

History of selected administrative and operational actions.
